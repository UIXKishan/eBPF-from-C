01

Nine stages from source file to running kernel code

eBPF lets you add logic to the kernel without writing a kernel module. The trick is that the kernel never trusts your code: it checks every path before turning it into machine instructions.

03

Inside one 64-bit instruction

Every eBPF instruction is exactly 8 bytes: an opcode, two 4-bit register numbers, a 16-bit offset and a 32-bit immediate. Pick an instruction to decode the bytes the kernel actually receives.

05

The JIT maps eBPF registers straight onto CPU registers

eBPF was designed to look like a real CPU. Its eleven registers line up with the x86-64 calling convention, so most instructions become one or two native instructions and helper calls become plain calls.

What the kernel does with the JIT image

Once the verifier approves, bpf_int_jit_compile() emits native code in a few passes until the jump offsets stop shrinking.

prologue
A 5-byte nop at the entry lets the kernel later patch in a trampoline, so other BPF programs (fentry/fexit) can trace this one.
memory
The image is placed in executable, read-only memory. Nothing can rewrite it after load.
hardening
net.core.bpf_jit_harden enables constant blinding, so attacker-chosen immediates never appear raw in executable memory.
fallback
Without a JIT, an in-kernel interpreter runs the bytecode. Kernels built with CONFIG_BPF_JIT_ALWAYS_ON remove the interpreter entirely.
arches
x86-64, arm64, riscv, s390, powerpc, loongarch and more each have their own JIT backend for the same bytecode.

08

Why not just write a kernel module?

Both run code in the kernel. The difference is who carries the risk.

Kernel moduleeBPF program
SafetyA null pointer or infinite loop can crash or hang the whole machine.Verifier rejects unsafe memory access, unbounded loops and bad return values before load.
PortabilityRebuilt against each kernel's headers; internal APIs change without notice.CO-RE and BTF relocate struct offsets at load time: compile once, run on many kernels.
Deployinginsmod; a bug means a reboot.Loaded and detached at runtime, swapped atomically through bpf_link.
What it can callAny exported kernel symbol.Only helpers and kfuncs the kernel allows for that program type.
SpeedNative.Native after JIT; XDP runs before sk_buff allocation, so it is often faster than equivalent stack logic.
PrivilegeCAP_SYS_MODULECAP_BPF plus CAP_PERFMON or CAP_NET_ADMIN depending on program type (Linux 5.8+).
09

Commands to see this on your own machine

Compile with BTF debug info

clang -O2 -g -target bpf -c xdp_count.bpf.c -o xdp_count.bpf.o

Read the bytecode LLVM produced

llvm-objdump -d xdp_count.bpf.o

Load and attach to an interface

sudo ip link set dev eth0 xdp obj xdp_count.bpf.o sec xdp

Bytecode after the verifier rewrote it

sudo bpftool prog dump xlated name count_packets

The native machine code the JIT emitted

sudo bpftool prog dump jited name count_packets

Read the counter from user space

sudo bpftool map dump name pkt_count
Bytecode and verifier output follow LLVM and Linux 6.x conventions. Exact addresses, map IDs and offsets such as 0x110 differ between kernels and builds.
